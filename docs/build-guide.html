ゴール

何が「できあがる」の？

ブラウザで動く、お店のレジです。最後にはこれが全部あなたの手で動きます。

商品をタップ

並んだ商品を押すとカートに入る。数量を増減できる。

税と値引き

軽減税率 8% / 10% を分けて計算。単品にも全体にも値引き。

現金会計

預かり金を打つとお釣りを計算。レシートも出る。

記録が残る

売上も商品も、ブラウザを閉じても消えない（保存される）。

プログラムは4つの役割に分けて作ります。レストランに例えると、それぞれの担当がはっきりします。下から上へ、内側から外側へ。

4

UI ＝ 客席とメニュー表

lib/ui/

lib/state/
2

商品・売上・途中のカートを保存して取り出す係。データベース担当。

ドメイン ＝ 厨房（計算の心臓）

税・値引き・お釣りを正確に計算する純粋なルール。画面も保存も知らない。だから一番に作る。

lib/domain/

先に知っておくと楽な言葉

用語ミニ辞典

全部覚えなくて大丈夫。地図の中で出てきたら、ここに戻ってくれば OK。

Dart
ダート

Flutter で使う言語。文章でいう「日本語」にあたる、書くための言葉。

Flutter
フラッター

1つのコードでスマホ・Web・PC アプリを作れる道具箱。今回は Web で動かす。

Widget
ウィジェット

画面の部品。ボタンも文字も並びも全部ウィジェット。積み木のように組む。

State
状態（ステート）

「今こうなっている」という変わりうる情報。カートの中身など。

Provider
プロバイダ

状態を画面のあちこちに配って、変わったら自動で描き直す仕組み。

SQLite / drift
データベース

データを表として保存する小さな金庫。drift はそれを Dart から安全に使う道具。

Pure function
純粋関数

同じ入力なら必ず同じ答えを返し、外に副作用がない計算。テストしやすい。

TDD
テスト駆動

「答え合わせ（テスト）」を先に書いてから中身を作る進め方。安心して進める。

作る順番

ロードマップ ― 6つの駅をめぐる旅

一気に作ろうとしないこと。駅ごとに「動く小さな成果」を積み上げます。各駅に 何を / なぜ / 新しく出会う概念 / つまずき注意 を書きました。

Phase 0

下ごしらえ ― 箱を用意する

空のプロジェクトを作り、ブラウザで真っ白でも「起動した」を確認する。

何を

Flutter を入れ、新しいプロジェクトを作成。Web で動くか1回試す。

なぜ

土台が動かないまま機能を足すと、原因が「自分のコード」か「環境」か分からなくなる。

出会う概念

プロジェクト構成、pubspec.yaml（部品リスト）。

つまずき注意

最初の起動は遅い。フリーズではないので待つ。

flutter create pos_demo  →  flutter run -d chrome
Phase 1

計算の心臓 ― 数字を正しく

税・値引き・お釣りの計算だけを、画面なしで作る。先に「答え合わせ」を書く。

何を

商品・明細・値引きの「型」を作り、computeReceipt という計算関数をテスト付きで育てる。

なぜ

お金の計算が1円でも狂うと致命的。画面より先に、ここを鉄壁にする。

出会う概念

純粋関数、TDD、整数で円を扱う、1円未満の切り捨て。

つまずき注意

小数で金額を持つと誤差が出る。整数（円）で計算するのが鉄則。

テストファーストのコツ

「1000円の8%は税80円」のような例を先に書く → 失敗を確認 → 通るように中身を書く。これを小さく繰り返すと、後戻りがほぼ無くなる。

Phase 2

記憶する ― 倉庫を建てる

商品・売上・途中のカートを保存・取り出しできるようにする（データベース）。

何を

表（テーブル）を定義し、保存／読み出し係（リポジトリ）を作る。drift がコードを自動生成。

なぜ

「閉じたら消える」では実用にならない。会計記録は消えてはいけない。

出会う概念

テーブル、リポジトリ（DB をしまう箱）、コード生成、スナップショット保存。

つまずき注意

Web で SQLite を使うには専用ファイル（WASM）の配置が要る。ここが最初の関門（下のつまずき集参照）。

dart run build_runner build  →  表の Dart コードが自動で生まれる
Phase 3

司令塔 ― 計算と倉庫をつなぐ

「カートに入れる／数量を変える／会計する」操作を持つ司令塔（状態）を作る。

何を

ChangeNotifier を使い、操作のたびに計算（Phase1）を呼び、保存（Phase2）し、画面へ「変わったよ」と知らせる。

なぜ

画面に計算や保存を書くと散らかる。1か所に集めると追いやすい。

出会う概念

状態管理、provider、通知（notifyListeners）。

つまずき注意

状態を直接いじらず、必ずメソッド経由に。保存と通知をセットで動かすため。

Phase 4

画面 ― 触れる形にする

商品グリッド・カート・会計ダイアログ・レシート・売上・商品管理を組む。

何を

ウィジェットを積んで画面に。司令塔（Phase3）を「見て」描き、タップで操作を呼ぶだけ。

なぜ

中身（計算・保存・状態）が完成しているので、画面は安心して薄く作れる。

出会う概念

ウィジェットの組み立て、Material（既製の見た目）、ダイアログ。

つまずき注意

非同期処理の後に画面が閉じている場合がある（mounted 確認が必要）。

Phase 5

仕上げ ― 通しで確かめる

最初から最後まで実際に触り、リロードしても残るかを確認。気になる所を磨く。

何を

レジ打ち→値引き→会計→お釣り→レシート→売上→商品管理を通しで確認。リロードして保存も確認。

なぜ

部品が動いても、つないだ時に初めて気づく不具合がある。

出会う概念

結合確認、手で触る検証、コードの読みやすさ仕上げ（コメント整備）。

つまずき注意

「動いた」で満足せず、変な金額・空カート・お釣り不足など意地悪な操作も試す。

迷ったら思い出す

なぜ「画面」を最後に作るの？

エンジンが先、ダッシュボードは後

車は、メーターの飾りより先にエンジンが要る。アプリも、見た目より先に「正しく計算して保存する中身」を作る。中身が固いほど、画面づくりは速く・安全になる。

テストできる所から作る

計算は画面なしで「答え合わせ」ができる。だから一番テストしやすい計算を最初に固める。画面は人の目で確かめる部分が多いので、最後に回すのが効率的。

先回り

つまずきポイント集

多くの初心者がここで止まります。先に知っていれば、止まりません。

Web で SQLite を使うには一手間

スマホ用の方法は Web で動きません。drift の「Web セットアップ」に従い、sqlite3.wasm と drift_worker.js を web/ に置きます。バージョンを合わせるのがコツ。

金額は「整数の円」で

小数（0.08 をかける等）で持つと、ほんの少しの誤差が積もって合計がズレます。円を整数で扱い、税は ×8÷100 のように計算して切り捨てる。

コードを変えたら自動生成も作り直す

drift の表を直したら build_runner を再実行。生成ファイル（*.g.dart）は手で編集しない。

環境によって実行方法が変わる

例えば WSL（Windows 上の Linux）から Windows 側の Flutter を使う場合、コマンドの呼び方やプロジェクトの置き場所に癖があります。自分の環境で「最初の1回」を必ず通してから先へ。
